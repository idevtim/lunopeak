# LunoPeak — Claude Code instructions

Local-first dev dashboard. Tauri 2 (Rust shell) + React 19 + TypeScript + Vite + Tailwind 4.

## Commands

- `npm run dev` — Vite-only. UI mounts with `api.*` fallbacks; no Rust runtime.
- `npm run tauri:dev` — full app. First Rust compile takes minutes; subsequent runs are fast.
- `npm run typecheck` — `tsc -b --noEmit`.
- `npm run build` — `tsc -b && vite build`.
- `npm run tauri:build` — platform bundles to `src-tauri/target/release/bundle/`. Unsigned, no release.
- `npm run dist:mac` / `dist:win` / `dist:nix` — full end-to-end release per platform: preflight (version triple + `release-notes/vX.Y.Z.md`), build, sign, and draft the GitHub release. `build:mac` / `build:win` / `build:linux` are aliases. `dist:mac` first runs `scripts/prune-target.sh`, which wipes every debug/release cache under `src-tauri/target/` once per version (stamp: `target/.last-dist-version`; `LUNOPEAK_PRUNE=force|skip` overrides), and runs it again (forced) after a successful release so the per-arch caches it filled don't linger; the universal bundle dir with the DMG is kept. `dist:nix` (`build-linux.sh`, also inside the Docker target volume) and `dist:win` (`build-windows.ps1`, a PowerShell mirror of the script) prune the same way after a successful upload. Pruning always keeps each release dir's `bundle/`, where the installers live. A failed run, or a `--build-only` / `SKIP_RELEASE=1` Linux run, keeps its caches so the next run stays incremental. `LUNOPEAK_PRUNE=skip` skips every prune.
- `dist:nix` dispatches on the host: `build-linux.sh` natively on Linux, `docker-build-linux.sh` in an amd64 container on macOS. `-- --build-only` skips the tag/upload (`dist:nix:docker` forces the container path). See [docs/RELEASE.md](docs/RELEASE.md#building-linux-from-macos).

## Architecture

- **Cargo workspace:** `src-tauri/` is the workspace root and the app package. Scanners, models, pricing, the status line, `feeds` and the logger live in `crates/core` (`lunopeak-core`, no Tauri); the app re-exports them at its crate root, so `crate::scanners::…` / `crate::models::…` / `crate::elog!` work unchanged. Only Tauri-bound code stays in `src-tauri/src` (commands, settings, tray, snapshots, the `logger::init` wrapper). Keep core free of GUI crates: `cargo tree -p lunopeak-node -e normal | grep -iE 'tauri|wry|gtk|webkit'` must print nothing. Run `cargo test --workspace`; plain `cargo test` in `src-tauri` only runs the app's 15 tests. The single version source stays the first `version =` line of `src-tauri/Cargo.toml` (release scripts grep it); core's `build.rs` exports it as `LUNOPEAK_VERSION` / `lunopeak_core::VERSION`.
- **Remote machines (`crates/node`, `lunopeak_core::node_wire`):** `lunopeak-node --out <shared dir>` runs the core scanners on another machine and writes `<dir>/nodes/<machine id>/live.json` (every `--interval`, written only on change plus a 60s heartbeat) and `sessions.json` (each `--sessions-interval`, only on change), each in a versioned `Envelope` (`node_wire::SCHEMA`). Machines are identified by `node_wire::machine_id`: 32 hex chars created once in the app dir's `machine-id` (`create_new`, since the window, menu-bar process and node race), shared by the app and a node on the same machine so the hub never shows itself. The display name (`--name`, default the host name's first label, `clean_name`d) travels in the envelope and isn't unique. Sessions travel as `RemoteSession`, which carries the `#[serde(skip)]` `cost_by_day` / `cost_by_branch` / `cost_by_slot` alongside. `cost_by_slot` (`SlotSpend`: 15-minute UTC slots, filled by both scanners next to `cost_by_day`) lets `into_session` rebuild the days in the hub's own time zone. Unless `--share-prompts`, `node_wire::redact_live` / `redact_session` drop every free-text field before writing (`first_prompt`, todo text, subagent descriptions, session titles in `LiveContext.name`, and any summary that isn't a path, command, pattern, skill or URL, which covers Cursor chat and unknown/MCP tools' first-argument fallback); Whether or not prompts are shared, `node_wire::scrub_live_secrets` / `scrub_session_secrets` run every Bash and WebFetch summary and each `bash_commands` key through `scrub_command` (known key prefixes, secret-named `NAME=value` and `--flag value`, the password in `-u user:pass`, `Bearer x`, URL userinfo and secret query params, long random-looking words; deliberately not `-p` or a bare `-u`, which mean other things in cargo and git). `logger::scrub_secrets` stays the weaker log scrubber. `live.json` compares `node_wire::live_fingerprint` (process runtime/memory zeroed) so an idle machine isn't rewritten each tick. Rows get `host: Some(name)`; `host` is `None` everywhere for this machine and is never set by scanners. Agent toggles come from the app's settings.json on that machine if present. The node never touches credentials (`usage`, `cursor_web`, `codex_web`) and makes no outbound connections. Every `dist:*` script builds the node for its targets and attaches it under a version-free name (`lunopeak-node-macos-universal.tar.gz`, signed with the hardened runtime and notarized but not stapled since it's a bare binary; `lunopeak-node-linux-<arch>.tar.gz` for x86_64 and aarch64, built static against musl (`<arch>-unknown-linux-musl`, `musl-tools` in the build image) because a glibc build from the Ubuntu 22.04 container won't start on Debian 11 / Proxmox 7. The amd64 image only builds x86_64, so `docker-build-linux.sh` first builds aarch64 natively in `docker/Dockerfile.node-build` (`--platform linux/arm64`, own target volume) and mounts it as `LUNOPEAK_EXTRA_NODES`; `build-linux.sh` fails before tagging if any `lunopeak-node-linux-*` name in `install-node.sh` isn't among its node assets (2.6.0 and 2.6.1 shipped without aarch64, so ARM Linux installs 404'd until it was attached by hand); `lunopeak-node-windows-<arch>.zip`, unsigned like the app's NSIS installer), plus `scripts/install-node.sh` / `install-node.ps1` (only dist:mac and dist:nix upload the `.sh`, and both fail on a CR in it: a Windows checkout made it CRLF in 2.6.0; `.gitattributes` pins `*.sh` to LF), so `releases/latest/download/<name>` always works and the installers match the release. The installers download the right asset, run `lunopeak-node install` (extra args pass through), and on a first install run `pair`. `lunopeak-node install [run flags]` (`crates/node/src/service.rs`; `--listen` added when neither `--listen`/`--bind` nor `--out` is given) copies the binary to `<state dir>/bin/` and registers it for whoever runs it: a LaunchAgent `com.lunopeak.node` (`launchctl bootstrap gui/<uid>`), a systemd user unit `lunopeak-node.service` (suggests `loginctl enable-linger` for servers), or for root (Proxmox) a system unit in `/etc/systemd/system` with `HOME` set, since root shells there often lack a user bus; no systemd means a clear error, or a Task Scheduler logon task "LunoPeak node" run through `conhost.exe --headless` so no console opens. `uninstall` and `status` mirror it. Settings → Add a machine shows both one-liners with copy buttons.
- **Hub (`lunopeak_core::hub`, Settings → Agents & projects → Other machines):** `settings.remote` (`RemoteHubPrefs { enabled, folder }`) points at the shared folder. `get_remote_nodes` / `get_remote_live` / `get_remote_sessions` read it through a `Hub` cache keyed by mtime+size; they are deliberately separate from the local commands, because Ports, Repos, Worktrees, the dashboard, Insights and costs join on cwd or pid alone and must never see remote rows. Only Live, Sessions and Costs merge them (and Settings lists nodes). Costs uses `get_machine_costs` (`hub::machine_costs`: the combined `CostBreakdown` plus per-machine `MachineCost` rows; `None` when the feature is off) behind an All machines / This machine switch; project rows only open their detail page in the This machine scope, since `get_repo_cost_detail` reads local logs. The reader only looks at folders named like a machine id, checks the header (`schema`, `machineId` == folder name) before parsing `data`, reads only the exact file names, caps size, skips the hub's own `node_wire::local_machine_id()`, labels each node by its published name (`unique_labels` appends the shortest distinguishing id prefix when two share a name, because the views key rows by label), overwrites every row's `host` with that label, and drops session ids seen locally or on an earlier node. Live rows count only while the hub saw `generatedAt` change within `LIVE_STALE` (3 min); sessions are kept regardless. Remote items carry `MachinePill` (violet, `src/components/ui/MachinePill.tsx`) on every surface: Live cards and feed, Sessions rows, Costs project rows (`RepoCost.hosts` / `onThisMachine`, since rows group by project name and can mix machines). Live gives a remote session active in the last 10 min its own card when no remote process claimed it (pid < 0, `runtimeSec` -1, no memory). Remote rows are read-only in the UI: no Stop / reveal / open-in-editor, no memory-flat idle guess, no replay (the transcript stays on its machine; clicking explains). Pids are keyed `(host, pid)`. The tray, status line snapshot and budget alerts stay this machine only. Smoke-test a folder with `LUNOPEAK_HUB_ROOT=/path cargo test -p lunopeak-core hub_live -- --ignored --nocapture`.
- **Direct pairing (`lunopeak_core::direct`, `src/direct_link.rs`):** `lunopeak-node --listen [--bind ADDR[:PORT]]` (default `0.0.0.0:47390`) serves the same envelopes the publisher writes (to `<state dir>/outbox/`, one code path, so redaction can't be skipped) over TLS on a hand-rolled one-request-per-connection HTTP/1.1 (`/v1/hello`, `/v1/pair/{start,finish}`, `/v1/files/{live,sessions}.json` with ETag, `DELETE /v1/pair`). Each machine has a self-signed rcgen cert in its state dir named by machine id. `lunopeak-node pair` opens a pairing window (`pairing.json`: 6-digit code, 10 min, `PAIR_ATTEMPTS` = 5, each `/pair/start` uses one) that the running server reads. Pairing is SPAKE2 over the code (no offline guessing from a recorded exchange), then each side MACs the cert fingerprint *it* saw, so a man in the middle with its own cert fails; both derive a bearer token from the key, the sharer keeps only its SHA-256 (`paired-hubs.json`), the hub keeps the token and the pinned fingerprint in `paired-machines.json` (0600, not settings.json). The client verifier (`PinnedCert`) still checks TLS signatures. Crypto is `ring` only: `cargo tree -i aws-lc-sys` must stay empty (no C toolchain for the Windows/Linux builds). In the app, `direct_link::start` (window process only) starts a fetch every 5s (`DirectLinks::wake` for now) for each paired machine without one in flight, each on its own thread (`fetch_one`, also called synchronously by `pair_machine`), so a dead machine's connect timeouts never delay the others; link state changes are logged under scope `direct`. Fetches land in `<app dir>/remote-cache/nodes/<id>/`, writing only on change, and `remote_root` hands the hub `[remote-cache, shared folder]`; `Hub::refresh` reads a machine found in both roots from the first. Settings → Other machines merges `get_paired_machines` with `get_remote_nodes` by machine id; `probe_machine` / `pair_machine` / `unpair_machine` drive "Add a machine". `machine-id` carries a `hw <tag>` line (hash of `IOPlatformUUID` / `/etc/machine-id` / `MachineGuid`); a mismatch (app folder copied to another computer) makes a new id, and with it a new cert. Discovery (`lunopeak_core::discovery`, pure-Rust `mdns-sd`): the node advertises `_lunopeak._tcp` (instance name = machine id, TXT `id` / `name` / `v`) only when bound to an unspecified address; the app's `Discovery` browser starts on the first `get_discovered_machines` call (so the macOS Local Network prompt waits until someone opens Add a machine). `Discovered.addrs` keeps every usable address ranked 192.168 → 10/8 → 172.16/12 → other v4 → global v6 (VM and Docker adapters advertise too) and Settings probes them in turn. `src-tauri/Info.plist` (merged by Tauri) holds `NSLocalNetworkUsageDescription` and `NSBonjourServices`; `embed-menubar-helper.sh` copies both into the menu-bar helper's Info.plist (it does the serving and advertising; 2.6.0 shipped it without them). `discovery::local_addresses` feeds `ShareStatus.addrs` and the node's `status` / `pair` output, for pairing by address. Live mDNS round trip: `cargo test -p lunopeak-core discovery_live -- --ignored --nocapture`. Test locally with a second node: `lunopeak-node --listen --bind 127.0.0.1:47391 --state-dir /tmp/x --name "Test box"` and `lunopeak-node pair --state-dir /tmp/x`.
- **Share this machine (`src/sharing.rs`, `lunopeak_core::share`, `settings.share: SharePrefs { enabled, name, sharePrompts }`):** the app doing `lunopeak-node --listen`. `share::Publishers` (collect → redact unless `share_prompts` → envelope → write only on change, plus the 60s live heartbeat; a changed name or prompt setting rewrites) is the one publishing path for both the node and the app. `sharing::start` runs in the always-up process: the menu-bar agent on macOS (started before its early return in `setup`), the single process on Windows/Linux (`cfg(not(macos))` in the window branch). Each 5s tick it reads settings through `SettingsCache`, (re)starts `direct::serve` on `0.0.0.0:47390` plus the mDNS advert when off or renamed, writes to `<app dir>/outbox` (and the shared folder's `nodes/<id>/` when one is set), reusing the app's managed session caches, and writes `sharing-status.json`, which `get_share_status` reads in the window process (stale after 20s → not running). Settings → Share this machine opens the pairing window (`open_share_pairing` writes the same `pairing.json` the server reads), shows the code with a countdown and lists/removes paired apps (`get_share_hubs` / `remove_share_hub`, from `paired-hubs.json`). `lunopeak-node --listen` with the default state dir uses the same app dir and port, so only one of them can share; the second reports the port in use.
- **Routing single source of truth:** `src/routes.ts`. Sidebar entries, hash routes, and view registration all derive from it. Add new views by registering them here.
- **Typed IPC boundary:** `src/lib/tauri.ts` exposes an `api` object that invokes Rust commands in `src-tauri/src/commands.rs`. When running outside the Tauri runtime (`npm run dev`), `api.*` returns inline fallbacks so the UI still mounts in a browser tab.
- **Serde contract:** Rust models in `src-tauri/crates/core/src/models.rs` use `#[serde(rename_all = "camelCase")]`. Their TS mirrors live in `src/types/api.ts` — keep them 1:1 when editing either side.
- **Every view is wired.** All sidebar destinations render live data. The `_placeholder` view is kept only as the fallback for a route that lacks an implementation.
- **Multi-agent live activity:** `LiveEvent` / `SessionLiveState` carry an `agent` field (`LiveAgent = "claude" | "codex" | "cursor"`). The Claude scanner reads `~/.claude/projects/`; the Codex scanner (`scanners/live_codex.rs`) reads `~/.codex/sessions/**/rollout-*.jsonl`; the Cursor scanner (`scanners/live_cursor.rs`) opens Cursor's SQLite chat DB at `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` (and platform equivalents) read-only — mining `ItemTable["composer.composerHeaders"]` for sessions and `cursorDiskKV` for bubble-by-bubble messages. Cursor doesn't expose structured tool logs, so events surface as generic Chat / User messages. `commands::get_live_activity` merges all three feeds, gated on `claude_enabled` / `codex_enabled` / `cursor_enabled` (see `settings::AgentSources`). `lunopeak_core::feeds` holds that merge (and the context and process merges) so the node shares it. In `LiveView.tsx`, sessions are bucketed by `(host, cwd, agent)` and pids keyed by `(host, pid)`, so a codex process never shows a claude session's last action when multiple agents run in the same folder, and two machines never mix.
- **Subagent spend rolls up:** Claude Code writes each subagent run to `<project>/<session-id>/subagents/agent-*.jsonl`; the parent transcript records only the result, not the tokens. `sessions::subagent_files` finds them, and both `sessions::scan_all` (cost view, replay, today's total) and `usage::claude_usage` (5h/7d windows) fold their tokens and cost into the parent. Messages and tool stats stay main-thread. The session cache stamp covers subagent mtimes, so a finishing subagent re-parses its parent.
- **Live subagents:** `scanners::live::collect` lists every `<session>/subagents/` folder each poll (appends don't bump a folder's mtime, so it can't be gated on that), tail-reads only `agent-*.jsonl` touched in the last 10 min, and attaches them to the parent as `SessionLiveState.subagents` — subagent lines carry the *parent's* `sessionId`, so never feed them through `parse_recent`. `agent-<id>.meta.json` gives `agentType` / `description` / `model` (else `pickedEffortModel`); `finished: true` appears only once done (absent, not false, while running). Feed events from subagents set `LiveEvent.subagentId`; `LiveContext.subagentsRunning` drives Home / tray / Sessions; `SessionDetail.subagents` (`SubagentRun`) feeds the replay card.
- **Session parse cache persists across launches:** `sessions::scan_all` keeps parsed sessions keyed by transcript path and a `Stamp` (newest mtime across the main and subagent transcripts, plus the subagent count), re-parses only stale entries in parallel, and saves them to `sessions-cache.json` in the app dir. The window and menu-bar processes share that file, so writes go to a pid-suffixed temp file and are renamed into place. `DISK_CACHE_VERSION` includes the app version (`LUNOPEAK_VERSION`, which core's `build.rs` reads from `src-tauri/Cargo.toml`, not core's own `CARGO_PKG_VERSION`), so every release re-parses once; bump its `/N` suffix for parser changes made between releases. `usage::claude_usage` keeps its own in-memory mtime cache (`CLAUDE_TURNS`) for the 5h/7d windows.
- **Per-session context %:** `commands::get_live_contexts` → `LiveContext` rows (Live view, tray "Running now", dashboard). Claude maps pid → session exactly via `~/.claude/sessions/<pid>.json` (stale files outlive their process — liveness is checked), then tail-reads the transcript's last main-chain assistant turn: `input + cache_creation + cache_read` over a model-inferred window (`live::claude_context_window` — transcripts don't record it). Codex uses the rollout's last `token_count` (`last_token_usage.total_tokens / model_context_window`), paired to running codex processes by cwd. Cursor uses per-composer `contextUsagePercent`.
- **Terminal status lines (`src-tauri/crates/core/src/statusline.rs`):** the app binary doubles as Claude Code's `statusLine` command — `main.rs` dispatches `LunoPeak statusline [--chain]` before any Tauri setup (keep it that way; it runs on every repaint, ~10ms). It renders from stdin + app files only (`usage-cache.json` for Fable, `statusline-snapshot.json` for today's cost, refreshed by the tray loop), never the network, and records each session's real window to `claude-contexts/<session_id>.json`, which `live::contexts` prefers over the model heuristic. Layout comes from `settings.statusline` (`StatuslinePrefs`: segment order/on-off, style, thresholds), which the CLI reads straight out of the app's settings.json; `render_spans` returns toned spans that the CLI turns into ANSI and Settings renders as its live preview (`preview_statusline`; `demoFixtures.previewStatusline` mirrors it for browser mode). Install/uninstall edits `~/.claude/settings.json` (chaining + restoring any existing status line) and `~/.codex/config.toml` `[tui] status_line` via `toml_edit` (Codex has no custom-command status line).
- **Status line owl:** `render_spans` opens with `OWL_IDLE` or a frame of `OWL_FLAP` (one per wall-clock second, all the same width) when `prefs.owl`. `session_working` decides between them from the stdin `transcript_path`, because Claude Code sends no busy flag: `turn_in_progress` walks the tail back to the last `system/turn_duration` (done), assistant (open unless `end_turn` or an `AskUserQuestion`), or user line (open unless "[Request interrupted"). A running subagent also counts as working. The install writes `refreshInterval: 1` so the owl animates, and `statusline::ensure_refresh` adds it to older installs at launch. `OWL_FLAP` is mirrored in `src/lib/statusline.ts` for the Settings preview.
- **Insights (`scanners/insights.rs`, `views/insights/`):** GitHub-Pulse-style stats across every tracked repo, drilled into one repo via `#/insights?repo=<path>&days=N`. Two commands so the page paints without the network: `get_repo_insights` runs local `git log --no-merges --numstat` over the default branch (`origin/HEAD`'s branch, unioning the remote-tracking ref and the local branch, never fetching; `lastFetchMs` from `.git/FETCH_HEAD` says how fresh that is) and folds in Claude sessions/cost by repo path; `get_pr_insights` makes one `gh pr list --state all --search updated:>=…` per github.com repo (limit 1000), cached 5 min per period in `InsightsPrCache`, and reuses `GithubCache`'s open-PR list for "open now". `Period` buckets by hour (24h), local calendar day (≤31 days) or week; PRs are bucketed in TS against the git query's `buckets` so cached PR data can't drift a slot. The gh query skips `additions,deletions` on purpose: they make it ~8× slower. Agent-commit counts come from `Co-authored-by` trailers and are a lower bound. **Per-PR cost:** `Session.cost_by_branch` bills each assistant turn (subagent turns included, falling back to the parent's branch) to its `gitBranch`, as a per-minute timeline (`BranchSpend`, `#[serde(skip)]` off IPC, carried in the disk cache row like `cost_by_day`). `insights::attach_pr_costs` sums it per merged PR's `headRefName` in that repo over the minutes after the previous merge of the same branch name (at most 14 days before the PR opened) up to this PR's merge, so a session that keeps going after a merge bills the rest to the next PR from that branch, or to nothing. PRs from the default branch get none. It runs on every `get_pr_insights` call, after the 5-min gh cache, so costs never go stale. Smoke-test against a real repo with `LUNOPEAK_INSIGHTS_REPO=/path cargo test -p lunopeak-core insights_live -- --ignored --nocapture`.
- **Process relabeling:** `scanners::processes::TARGET_NAMES` is `["claude", "codex", "cursor", "cline"]`. `match_target` returns the display name. When the match comes from an argv basename (a Node CLI like the `@openai/codex` or `@anthropic-ai/claude-code` npm package, where `proc.name()` is "node"), the row is relabeled to the matched target ("codex" / "claude"). Direct matches on process / exe basename keep `proc.name()` verbatim. Cursor's macOS helper fan-out (Renderer, GPU, Plugin) is collapsed into a single "Cursor" row via `collapse_helpers` — the top-level `Cursor.app` process has cwd `/Applications` and gets filtered by `is_project_cwd`, so without keeping helpers we'd see no Cursor row at all.

## App icon

Two pipelines, one per family of platforms:

- **Windows / Linux + legacy macOS** — `src-tauri/icons/source.png` (1024×1024 raster) → `npm run icons` → the PNG/`.icns`/`.ico` set listed in `tauri.conf.json`'s `bundle.icon`.
- **macOS 26+ (Liquid Glass)** — `src-tauri/icons/LunoPeak.icon/`, an Icon Composer bundle: `icon.json` + three flat SVG layers in `Assets/`. The glass comes from `icon.json`, not the artwork — a `fill` gradient for the sky, a flat back group (`specular: false`) holding moon and mountains, and a `glass: true` group holding the owl. Layers must stay **flat, shadowless, and full-bleed 1024×1024**: the system supplies the squircle, the shadow, the refraction and the specular pass, so anything baked into the art fights it.

macOS renders a different variant per appearance (Default, Dark, Clear ×2, Tinted ×2). By default it recolours unspecialized back-group layers from the `fill` gradient, which in Dark turns the moon navy — so the Moon layer pins `fill-specializations` (solid cream) and `opacity-specializations` (1.0) for `appearance: "dark"`. Those are per-layer arrays; an entry with no `appearance` key is the default. The full vocabulary (`hidden-`, `position-`, `specular-`, `blend-mode-`, … `-specializations`) is in `IconComposerFoundation`. Clear and Tinted are deliberately left automatic — they're meant to be uniform.

`scripts/embed-glass-icon.sh` compiles the bundle with `xcrun actool` (standalone — no Xcode project needed) and injects `Assets.car` + `CFBundleIconName` into the built `.app`, overwriting Tauri's flat `icon.icns` with actool's flattened fallback for pre-26 systems. `build-dmg.sh` calls it **before** `embed-menubar-helper.sh`, whose re-seal covers the modified `Contents/`.

`npm run icons:mac` renders every appearance to `src-tauri/icons/.preview/` and opens it. It shells out to Icon Composer's `ictool` by absolute path on purpose — **not** `xcrun ictool`, which resolves to a same-named actool sibling that has no `--export-image`, reports the unknown argument in a plist, and still exits 0. Test for the output file, never the exit code.

## Conventions

### Skeleton loading
Every async view exports a `<ViewNameSkeleton />` matching the shape of its real content. Views call `useDelayedLoading(isLoading)` so the skeleton only renders if data hasn't arrived within ~200ms — this avoids flash on fast loads. See `src/hooks/useDelayedLoading.ts` and `ReadoutSkeleton` / `RepoListSkeleton` for the pattern.

### UI primitives
Reach for existing components in `src/components/ui/` (`Skeleton`, `StatCard`, `SectionCard`, `ListRow`, `Badge`, `Button`) before adding new ones. Charts go through `src/components/charts/BarChart` — a thin-bar variant of Recharts. Layout chrome lives in `src/components/layout/` (`TitleBar`, `Sidebar`, `AppShell`).

### State
TanStack Query for anything backed by `api.*`. Zustand for ephemeral UI state. Don't introduce React Context for shared state.

## Gotchas

- Tauri capabilities are explicit — new IPC commands must be allowed in `src-tauri/capabilities/default.json` or they fail at runtime.
- Icons are committed (all of `src-tauri/icons/`), so a fresh clone builds. Regenerate with `npm run icons`, never `npx @tauri-apps/cli icon` directly — the CLI's `.ico` omits the 128px frame that Windows 11 picks for several shell surfaces, and `build-icons.sh` rebuilds it with ImageMagick.
- `tsconfig.tsbuildinfo` is gitignored but can cause stale build state — delete it if `tsc -b` behaves oddly.
- The frontend must keep working in plain browser mode (no Tauri). When adding `api.*` calls, also add a sensible fallback in `src/lib/tauri.ts`.
